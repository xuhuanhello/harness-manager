# Harness skill support registry

Researched against vendor documentation or vendor-owned repositories on 2026-09-23. The built-in records are in [`src/shared/harness-registry.ts`](../../src/shared/harness-registry.ts). The registry gives the manager explicit roots to inventory; it does not promise that every version of a product scans every listed compatibility root.

The primary user and workspace roots are where the manager installs: the location the vendor currently documents, or where its own installer writes. A product-specific root that the vendor keeps only for backward compatibility, such as Codex's `~/.codex/skills` or Goose's `~/.config/goose/skills`, is a read root even though only that product reads it. Two real copies of a skill in two roots a product reads can be listed twice: Codex deduplicates by canonical `SKILL.md` path, not by name, so an unqualified mention of a duplicated name selects neither copy. Goose and Amp keep the first skill with a given name in their scan order. Apply previews therefore point out an existing managed entry of the same skill in another root the selected Harness reads.

`readsUserAgents` and `readsWorkspaceAgents` are true only where the vendor documents the shared Agent Skills roots `~/.agents/skills` and `.agents/skills`. Support for installing a skill into a folder is not treated as evidence that a product discovers that folder. `extra*Skills*Paths` lists vendor-documented compatibility or legacy roots. Product-defined environment-variable roots and directory inheritance rules that cannot be represented by the current schema are called out below.

The `universal` record represents the shared Agent Skills convention itself: `~/.agents/skills` and `.agents/skills`, as specified by [Agent Skills](https://agentskills.io/specification). It is not an installed product.

Compatibility roots are stored alongside these primary roots in `extraUserSkillsPaths` and `extraWorkspaceSkillsRelativePaths`; this includes Cursor's `.claude`/`.codex` roots, OpenCode and Copilot's `.claude` roots, Codex's `.codex` roots, Goose's `~/.config/agents/skills`, and each product's documented legacy paths.

Codex roots were re-checked against `openai/codex` main at `ea647275` on 2026-09-27. `codex-rs/ext/skills/src/host_roots.rs` adds `$CODEX_HOME/skills` (commented as deprecated, kept for backward compatibility), `~/.agents/skills`, `/etc/codex/skills`, the `skills` folder of every project `.codex/` config folder between the project root and cwd, and `.agents/skills` in each of those directories. The project `.codex/skills` root is loaded but not listed in the public docs; the manager has not confirmed at runtime how Codex treats it in an untrusted project. The bundled skill installer and skill creator still write to `$CODEX_HOME/skills`; the registry follows the documented `.agents/skills` roots and treats both `.codex` roots as read roots.

Goose (re-checked 2026-09-27 at `block/goose` main `04ed836c`, `crates/goose/src/skills/mod.rs`) scans project `.agents/skills`, `.goose/skills`, `.claude/skills` in the current directory only, then `~/.agents/skills`, its config directory's `skills` (`~/.config/goose/skills` on macOS and Linux), `~/.claude/skills` and `~/.config/agents/skills`. Its docs list the Goose roots under backward compatibility, and its own writer uses the shared roots. Amp is closed source; its docs read `~/.config/agents/skills`, `~/.agents/skills`, `~/.config/amp/skills`, project `.agents/skills` with parents, `.claude/skills` and `~/.claude/skills`, and call the first two agent-agnostic roots that can be turned off with `amp.skills.disableGlobalAgentsSkills`. `amp skill add --global` writes to `~/.config/agents/skills`.

The `codex-app` record uses the same skill roots as Codex CLI, but has separate macOS app detection. The desktop app now ships as `ChatGPT.app` while keeping the bundle identifier `com.openai.codex`. Like OpenAI's [Codex CLI desktop-app resolver](https://github.com/openai/codex/blob/main/codex-rs/cli/src/desktop_app/mac.rs), the manager checks `ChatGPT.app` and `Codex.app` under `/Applications` and `~/Applications` and accepts a bundle only when its `CFBundleIdentifier` matches `appBundleIds` (`com.openai.codex`), so the classic ChatGPT app (`com.openai.chat`) is not treated as Codex.

## Detection metadata

- Cursor is split into desktop and CLI records. `Cursor.app` identifies the editor surface; the CLI record detects `cursor-agent --version` and its documented `~/.local/bin/cursor-agent` path. A `cursor-agent` executable alone does not imply the desktop app is installed.
- VS Code Copilot, Cline, and Roo Code use extension IDs rather than the `code` launcher. The launcher only proves that the editor exists. Their configured default extension roots are `~/.vscode/extensions` and `~/.vscode-insiders/extensions`, matching [VS Code's extension-location documentation](https://code.visualstudio.com/docs/configure/extensions/extension-marketplace). Custom `--extensions-dir`, profiles, and portable installations can use other locations; users can add those paths.
- Windsurf has been renamed Devin Desktop. `Windsurf.app`, `Devin.app`, and `Antigravity.app` entries are conventional macOS detection candidates inferred from the product names, not vendor-guaranteed bundle paths. Candidates are user-editable. Detection still requires a `.app` directory with an `Info.plist` and an executable; the registry does not infer installation from skill folders.
- The Antigravity CLI is a separate product surface (`agy`) with a distinct user skill root. It must not be merged with the desktop/IDE record.
- Version commands run directly, without a shell, with the inherited `PATH` plus the candidate's own directory, the common install directories searched for commands, and common Node.js runtime locations (nvm, Homebrew `node`/`node@N` kegs, fnm, mise, asdf). An app launched from Finder inherits only `/usr/bin:/bin:/usr/sbin:/sbin`, so npm-installed launchers such as `codex` and `pi` (`#!/usr/bin/env node`) would otherwise exit before printing a version. The per-Harness budget is 5 seconds because the first run of a freshly updated large signed binary, such as Claude Code's native build, was measured at 2.3 seconds in macOS verification.
- Registry changes to `executablePaths`, `appPaths`, and `extensionRoots` are merged into saved built-in records at startup, so newly added candidates reach existing installations. Locally added paths are kept.
- Residual directories listed for an undetected product exclude the shared `~/.agents/skills` and `.agents/skills` roots, which belong to the `universal` record, and other products' primary roots that the product only reads for compatibility (for example `~/.claude/skills` for Goose). When a listed directory is shared, the explanation names an installed reader first, then the universal record, then readers whose installation is unconfirmed, then disabled readers. Any registered reader, including a disabled one, still blocks cleanup.

## Exclusions and limitations

- xAI's official repository documents a product named **Grok Build**, with native `.grok/skills` and Agent Skills compatibility roots. This record refers to that coding CLI, not the general Grok chat product.
- Roo Code's official Marketplace listing currently says its extension shut down on 2026-05-15. The record remains to identify existing installations and preserve configured roots; it should not be presented as a currently installable extension.
- No Trae record is included. The [official Trae repository issue](https://github.com/Trae-AI/TRAE/issues/2253) requested native `SKILL.md` support and did not establish a discovery path; no current official page or repository source specifies one. Installer compatibility alone is insufficient evidence.
- Roo's mode-specific `skills-{mode}` folders, products' ancestor traversal, and configurable/environment-variable roots are not expressible as full discovery rules in the current path schema. The registry records the common directory roots and documents this boundary rather than implying complete emulation.
- The installation detector validates executable or app-bundle presence. It checks product identity only where the registry lists `appBundleIds` (currently Codex Desktop); other `.app` candidates are matched by bundle structure. App paths are discovery candidates, not official filesystem contracts.
- The registry does not record which product owns a legacy compatibility root. A compatibility root that is not another product's primary root, such as Cursor's `~/.codex/skills`, can still appear among that product's residual directories; it remains protected from cleanup by its registered readers.
